# BoxStack 정체성 방향 정리

마지막 갱신: 2026-05-25
상태: 방향성 초안
범위: 블록 색상, bevel, 질감, 그림자, 깊이 실험을 재개하지 않는 BoxStack 고유 정체성 후보 정리

## 배경

현재 수용된 기준은 Stack-like 2D 프로토타입이다. 추상 직사각형 블록, 조용한 세로 그라데이션 배경, 간결한 faux-glass HUD, 되돌리기 없음, 중앙 착지 토스트 없음, 바닥 접촉 기반 실패 판정, 안정성 기반 다음 박스 생성, B086 접촉 직전 낙하 속도 리셋을 사용한다.

이 기준은 읽기 쉽고, 거치된 박스의 x축 속도를 감쇠하던 B085보다 훨씬 자연스럽다. 다만 게임이 깨끗한 블록 쌓기와 스테이지 번호만으로 남으면 `Stack`의 단순 클론처럼 보일 위험이 있다. B081에서 색상, 명암, 블록 외형 실험을 멈추기로 했으므로, 다음 정체성 작업은 플레이 루프, 피드백 언어, 스테이지 프레이밍, 기록, 오디오, 햅틱 같은 축에서 찾아야 한다.

## 제약

- 블록 색상, 명암, bevel, pseudo-3D, 질감, face-split, 그림자, 코드별 시각 차이 실험을 재개하지 않는다.
- 정체성 작업의 일부로 되돌리기, 광고 보상 복구, 실패 팝업 이어하기를 되살리지 않는다.
- 특정 정체성 실험에 꼭 필요하지 않은 한, 물리 튜닝을 넓게 묶어서 바꾸지 않는다.
- 첫 App-in-Toss MVP는 첫 몇 초 안에 목표와 조작을 이해할 수 있을 만큼 가볍게 유지한다.
- 현재 모바일 safe-area 대응과 최소 HUD 방향을 유지한다.

## 후보 방향

### 1. 착지 정확도 감각

BoxStack을 단순히 블록이 쌓이는 화면이 아니라, 작은 정밀 조작 장난감처럼 느끼게 하는 방향이다. 정체성의 중심을 "얼마나 깔끔하게 놓았는가"에 둔다.

가능한 표현:

- 박스가 기존 탑과 얼마나 잘 겹쳤는지, 접촉 후 흔들림이 얼마나 적었는지로 착지 품질을 측정한다.
- `딱 맞음`, `안정`, `위험`, `흔들림` 같은 짧은 단어를 실제 상태를 설명할 때만 사용한다.
- 완벽하거나 거의 완벽한 착지는 진행 인디케이터나 스테이지 배지에 작은 pulse 정도로만 표현한다.
- 콤보나 streak은 나중 후보로 두고, 첫 실험에서는 점수 경제로 확장하지 않는다.

맞는 이유:

- 현재 사용자가 가장 민감하게 본 지점인 좌우 밀림과 탑 안정성 문제와 자연스럽게 이어진다.
- 시각 장식이 아니라 조작 실력으로 BoxStack의 개성을 만든다.
- 새 아트 에셋 없이 Editor Play에서 빠르게 확인할 수 있다.

위험:

- 매 낙하마다 피드백이 뜨면 제거했던 중앙 토스트처럼 소음이 될 수 있다.
- 점수를 너무 빨리 붙이면 스테이지 클리어 감각보다 숫자에 먼저 집중하게 될 수 있다.

권장:

- 가장 먼저 실험하기 좋은 후보.
- 첫 단계는 측정과 절제된 HUD 피드백까지만 둔다.

### 2. 타워 안정성 드라마

박스를 놓은 뒤 기다리는 시간을 의도적인 긴장으로 만든다. 플레이어가 기다리는 이유는 타워가 정말 안정됐는지 아직 결정되지 않았기 때문이다.

가능한 표현:

- 5초 클리어 검증과 post-drop 안정 대기 시간을 더 명확한 감정 흐름으로 만든다.
- 탑이 실제로 움직이는 동안에만 아주 작게 `안정 중` 같은 상태를 보여준다.
- 최대 대기 시간이 없는 현재 결정처럼, 계속 흔들리면 플레이어가 그 흐름을 보다가 자연스럽게 실패까지 받아들이게 한다.
- 결과 팝업 문구를 단순 clear/fail보다 탑 상태와 더 연결한다.

맞는 이유:

- B083과 B084의 핵심 규칙을 그대로 활용한다. 게임은 이미 실제 탑 안정성과 바닥 접촉 실패를 본다.
- 기다리는 순간이 죽은 시간이 아니라 긴장으로 읽힐 수 있다.
- 사용자가 의도한 "흔들리면 바라보다가 무너지면 실패" 사이클과 잘 맞다.

위험:

- 흔들림 중 UI가 많아지면 물리적 긴장이 줄어든다.
- 별도 게이지가 크면 다시 앱 상태 화면처럼 보일 수 있다.

권장:

- 착지 정확도 감각 다음으로 좋은 후보.
- 새 큰 게이지보다 기존 HUD의 작은 상태 변화나 짧은 문구가 낫다.

### 3. 블록 아트 없이 스테이지 성격 만들기

블록 외형을 바꾸지 않고, 스테이지 이름, 목표, 난이도 프레이밍으로 진행감과 개성을 준다.

가능한 표현:

- `입문`, `좁은 발판`, `흔들림 구간`, `장거리 이동` 같은 짧은 스테이지 라벨을 붙인다.
- 20개 스테이지를 난이도 리듬에 따라 작은 챕터로 묶는다.
- 스테이지 선택 팝업에서 다음 스테이지가 무엇을 요구하는지 한 줄로 보여준다.

맞는 이유:

- 수용된 시각 스타일을 건드리지 않고도 "기획된 진행" 느낌을 줄 수 있다.
- stage 10, 15, 20이 왜 다르게 느껴지는지 플레이어가 이해하기 쉽다.
- copy/data 중심이면 구현 부담이 낮다.

위험:

- 텍스트가 많아지면 미니멀 방향과 충돌한다.
- 실제 규칙 차이가 없는데 라벨만 강하면 가짜 개성처럼 느껴진다.

권장:

- 주요 스테이지 튜닝이 더 안정된 뒤에 적용하는 편이 좋다.
- 라벨은 짧고 기능적으로 유지한다.

### 4. 기록 추구

다시 플레이하고 싶은 이유를 개인 기록, 깔끔한 클리어, 후반 스테이지 숙련도에서 만든다.

가능한 표현:

- 최고 클리어 스테이지, perfect landing 수, 위험 착지 수 등을 기록한다.
- 스테이지 클리어 시 작은 기록 문구를 보여준다.
- App-in-Toss 리텐션이 필요해질 때만 일일 도전이나 세션 도전을 검토한다.

맞는 이유:

- 되돌리기나 광고 복구 없이도 반복 플레이 이유를 만들 수 있다.
- 고정 스테이지 MVP 위에 얹기 쉽다.

위험:

- 무엇이 깔끔한 착지인지, 위험한 착지인지 정의가 먼저 필요하다.
- 제품 데이터처럼 다루기 시작하면 저장, 분석, anti-tamper 질문이 빨리 따라온다.

권장:

- 착지 품질 측정이 먼저 생긴 뒤로 미룬다.
- 초기에는 로컬 프로토타입 기록으로만 다룬다.

### 5. 오디오와 햅틱 시그니처

화면을 복잡하게 만들지 않고, 짧은 소리와 촉감으로 BoxStack을 알아볼 수 있게 한다.

가능한 표현:

- 깔끔한 착지에는 짧고 부드러운 click.
- 불안정한 착지에는 낮고 둔한 thud.
- 위험한 흔들림이나 실패에는 작은 진동.
- 반복 플레이에서 피로하지 않은 아주 짧은 clear/fail cue.

맞는 이유:

- 같은 시각 기준도 훨씬 의도적으로 느껴질 수 있다.
- 모바일 플레이와 App-in-Toss의 즉시성에 잘 맞다.

위험:

- WebGL/App-in-Toss에서 햅틱 지원이 제한적이거나 별도 bridge가 필요할 수 있다.
- 소리는 반복 플레이에서 금방 거슬릴 수 있다.

권장:

- 좋은 polish 후보지만, 플랫폼 제약을 확인하기 전에는 1순위 실험으로 두지 않는다.
- 햅틱이 불확실하면 오디오부터 작게 시작한다.

## 권장 순서

1. 착지 정확도 감각
2. 타워 안정성 드라마
3. 스테이지 성격
4. 기록 추구
5. 오디오와 햅틱 시그니처

첫 구체 실험은 작은 착지 정확도 pass가 좋다.

- 기존 물리 상태를 사용해 착지 품질을 측정한다.
- 결과는 기존 HUD 안에서 절제된 방식으로만 보여준다.
- 중앙 토스트, 새 블록 외형, 점수 시스템은 첫 pass에 넣지 않는다.
- 사용자 주도 Editor Play로 확인한다. 좋은 착지가 더 의도적으로 느껴져야 하지만, 화면은 더 바빠지지 않아야 한다.

## 하지 않을 것

- 새 블록 아트 방향.
- visual skin swap.
- 광고 보상 복구.
- 되돌리기 복귀.
- 큰 UI 재설계.
- 착지 품질 감각이 검증되기 전의 전체 점수 경제.

## 성공 기준

- 다음 정체성 실험이 좁은 프로토타입 변경으로 구현 가능하다.
- 수용된 블록 비주얼을 바꾸지 않고도 "이건 BoxStack답다"는 이유가 생긴다.
- 현재의 깨끗한 모바일 UI가 붐비지 않는다.
- B084와 B086으로 개선한 물리적 쌓기 가독성을 유지한다.
